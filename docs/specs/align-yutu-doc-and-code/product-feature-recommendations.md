### 2.4 行业共性趋势（对语图最有参考价值的 7 条）

1. **「生成」已不是壁垒，「可编辑的增量修改」才是**。ProcessOn 的「智能迭代修改」、Eraser 的 diagram-as-code 双向同步、Lucid 的 Process Agent，都把竞争点从「一次生成」移到「持续演进」。语图的四级降级匹配正处在这条主线上，是稀缺资产。
2. **AI 自动修复/自查成为标配**。Mermaid Chart 的 Diagram Repair、Excalidraw 的 AI Repair、ProcessOn 的「AI 自查纠错」，都在解决「模型输出不合法/不可渲染」的最后一公里。语图已有反思校验 + Rewriter，但缺少**视觉层**自检。
3. **用 Schema/风格样例约束模型输出**（draw.io 的 `mxfile.xsd` + Style Reference）被证明比事后修补更有效。语图的 FlowDraft 中间结构是同一思路的更彻底版本（模型完全不碰坐标/样式/ports），架构上更领先。
4. **多模态输入是 2026 年国内产品的主战场**：拍照/草图转图（EdrawMax）、截图/论文/纪要理解（ProcessOn）、文件/链接/音视频（GitMind）、图片转可编辑（Eraser）。
5. **MCP 成为图表工具的标准集成面**：draw.io 4 条 MCP 路径、Excalidraw MCP Server、Miro Connectors、Lucid 接入 ChatGPT/Copilot。不接入 MCP ≈ 不在 AI 工作流里。
6. **企业采购看三件事**：数据留存承诺（Lucid 明示 30 天、不训练客户数据）、合规认证（SOC 2 / ISO27001 / GDPR / FedRAMP）、SSO/SAML 与审计。
7. **计费普遍转向「AI 额度」而非「席位」单一维度**：Napkin 周 credits、Whimsical AI actions、GitMind 算粒、Miro AI 额度。语图已有 Token 三级防护，具备直接产品化为额度体系的基础。

本节梳理语图**已具备的工程资产**，作为第四节所有建议的「衔接点」依据。原则：任何新功能都应优先复用既有基础设施，且**不引入新的基础设施硬依赖**（pgvector / Langfuse / Redis / @antv/layout / ES 均不作硬依赖，与规格关键决策一致）。

### R1 · 版本快照与可视化 Diff / 一键回滚

**功能点描述**
每次 AI 生成或增量修改落地前后，自动为项目图谱保存一份轻量快照（FlowDraft JSON + 布局结果 + 关联 `threadId` + 触发它的用户指令原文）。在编辑器侧提供「历史」面板：按时间倒序列出快照，支持三种操作 —— ①**预览对比**（当前画布 vs 选中快照，新增/删除/改名/改连线用不同色标叠加高亮）；②**一键回滚**到任意快照；③**逐条拣选回滚**（只撤销某几条 AI 操作项，保留其余）。快照列表每条都显示「本次 AI 做了什么」的自然语言摘要，而非裸时间戳。

**用户价值**
解决 AI 编辑类产品最致命的信任问题：**「AI 改坏了怎么办」**。当前用户面对不满意的 AI 修改只有两个选择 —— 手动一个个改回去，或推倒重来。有了快照与 diff，用户可以放心地让 AI 大胆尝试，因为任何一步都可逆。同时，「只撤销第 2、3 条操作项」这种细粒度回退，比全量回滚更贴合真实使用场景（AI 一次修改往往部分正确）。这也是从「一次性生成工具」升级为「可持续演进的图形工作台」的前提。

**实现难度评估：中**
- 理由：存储侧只是新增一张快照表（沿用现有 PG，无新依赖），FlowDraft 本身是纯 JSON、体积小，快照成本极低。真正的复杂度集中在 **diff 算法与可视化呈现**：需要把两份 FlowDraft 的差异映射为画布上的色标叠加，涉及节点/边的增删改四类状态判定与 X6 图层渲染。但这恰好是四级降级匹配的反向应用（匹配算法已经能判定「这两个节点是同一个」），不需要从零设计相似度算法。逐条拣选回滚需要把「操作项」作为一等公民持久化，涉及前端选择性应用状态的序列化。
- 依赖的现有模块：**A5 四级降级匹配**（diff 的核心引擎，L1–L4 匹配结果即差异对齐结果）、**A2 FlowDraft**（快照的数据格式）、**A12 内置 trace**（`threadId` 作为快照与对话轮次的关联键）、**A14 PG 存储范式**（快照表沿用令牌表同款可选 Redis / 缺省 PG 的写法）、前端选择性应用 UI（逐条勾选的交互与数据结构）。

**预期收益说明**
- 直接消除 AI 修改的不可逆风险，显著提升用户敢于使用 `modify` 意图的意愿（当前 modify 是语图最强的差异化能力，却因不可回退而被抑制使用）。
- Diff 视图是**四级匹配能力的可视化外显**：把后端已在计算但用户看不见的 `MatchLevel` 与残差清单变成界面语言，让「L2 语义匹配命中」「L4 边校验兜底」「未匹配残差」这些内部概念变成用户可感知的产品价值，是竞品无法轻易复制的展示面。
- 快照表天然成为**回归评估的语料来源**：真实用户的「AI 改坏了 → 回滚」事件是最高质量的 Bad Case 信号，可直接回流 A12 的 Bad Case 对比库，形成质量改进闭环。

**与现有能力的衔接点**
A5（diff 引擎 = 匹配算法反向使用）、A2（快照格式）、A12（trace 关联 + Bad Case 回流）、A14（存储范式）、A8（回滚结果可经 SSE 反馈进度）、前端选择性应用（逐条拣选回滚复用同一交互模型）。**不引入任何新基础设施依赖。**

**落地优先级：P0**
理由：R1 是 R2（选区改图）与 R5（多模态输入）的**安全前提** —— 这两项都会让 AI 的改动幅度变大，没有回滚能力就放大风险；同时 R1 是四级匹配这一核心资产唯一的可视化出口。应在 R2 之前或同期落地。

### R2 · 选区驱动局部改图 + 澄清追问（Plan Mode）+ consult 产品面

**功能点描述**
三个互相咬合的编辑体验改造，合为一条建议：

1. **选区进上下文**：用户在 X6 画布上框选或点选若干节点/边后，AI 浮窗自动感知选区，输入框上方显示 chip 提示「已选中 3 个节点：下单校验、库存扣减、支付网关」。此后用户的自然语言指令默认作用域收敛到选区（「把这几个合并成一个子流程」「这一段加个异常分支」），无需再重复描述位置。支持「仅选区 / 全图」作用域显式切换。
2. **澄清追问（Plan Mode）**：当意图识别判定为歧义、或指令缺少关键信息（如「优化一下这个流程」未说明优化目标）、或匹配置信度低时，AI **先反问再动手**，以卡片形式给出 2–4 个候选方向供点选（而非开放式提问），用户点选后恢复执行。追问最多一轮，仍不明确则给出保守默认方案并显式说明假设。
3. **consult 意图产品面**：把咨询意图从「纯文本气泡回答」升级为结构化呈现 —— 回答中涉及的节点自动在画布上高亮定位；涉及流程改进建议时，提供「按此建议修改」按钮，一键把咨询结论转为 `modify` 指令；提供「解释这张图」快捷入口，输出分层的流程说明（概览 → 关键路径 → 分支条件）。

**用户价值**
这三点共同解决**「AI 不知道我在说哪儿」**与**「AI 不懂装懂」**两个最高频的挫败来源。选区把「空间指代」从自然语言里剥离出来 —— 用户不必再写「把中间那个判断节点下面的第二个处理框改成……」，这是所有画布类 AI 产品的体验分水岭（Lucid Process Agent、Whimsical、ChatGPT Canvas 都以此为核心交互）。澄清追问则把「AI 猜错了 → 用户返工」变成「AI 问一句 → 一次做对」，Lucid 已将其作为 Plan mode 卖点。consult 产品面让「问」和「改」连成一条动线，而不是两个割裂的功能。

**实现难度评估：中**
- 理由：三项都属于**在既有机制上开产品面**，不需要新建 AI 能力。选区侧主要是前端工作（X6 selection 插件 → 提取 id 列表 → 注入请求上下文），后端只需在 modify 链路里把选区 id 作为匹配的优先锚点。澄清追问的机制**已经完全存在**（`need_confirm` + `candidates` + `resumeToken` 防重放），只需扩展触发条件（从「低置信匹配」扩到「意图歧义」「关键槽位缺失」）并设计候选生成 Prompt。consult 产品面主要是前端呈现与「建议 → modify 指令」的转换，后端 consult 意图已在跑。风险点是澄清追问若触发过频会打断心流，需要用 A12 评估集校准触发阈值。
- 依赖的现有模块：**A7 人在回路**（澄清追问的完整承载机制）、**A1 意图识别**（歧义/多命中检测点已存在，是追问的天然触发器）、**A5 四级匹配**（选区 id 直接作 L1 锚点，天然提升匹配准确率）、**A2 FlowDraft**、**A8 SSE**（追问卡片的流式下发）、**A11 记忆体系**（澄清答案写入长期记忆，同类问题下次不再问）、A16 全文检索（consult「解释这张图」可检索历史图）。

**预期收益说明**
- 选区作为 L1 锚点会**直接拉高四级匹配的 L1 命中率**，减少降级到 L3/L4 的比例，从而减少残差与确认打断 —— 这是「体验改善」与「质量指标改善」的同一动作，效果可在 A12 的四类指标上量化验证。
- 澄清追问把「生成结果不满意」这类**最难归因的失败**转化为「一次额外交互」，显著降低无效 Token 消耗（避免整轮重生成），与 R13 的额度体系形成正向关系。
- consult → modify 的动线打通会提升单会话轮次与留存（用户从「问完就走」变成「问完就改」）。
- 这三项是全矩阵中**竞品覆盖最广、语图缺口最明显**的组合（G1 + G15 + G16），补齐后编辑体验维度从「最大缺口区」跃升到与 Lucid 同档。

**与现有能力的衔接点**
A7（追问机制 = 人在回路的触发条件扩展，`resumeToken` 保证恢复执行不重放）、A1（歧义检测已有）、A5（选区 = L1 锚点）、A11（澄清答案入长期记忆，避免重复追问）、A8（卡片流式下发）、A2/A4（选区变更后的局部重布局）。**核心是复用，不是新建。**

**落地优先级：P0**
理由：G1 + G15 + G16 三项差距集中在编辑体验这一「最大缺口区」，且三项共享同一套人在回路机制、可一次性交付；同时它是提升四级匹配 L1 命中率的杠杆点，直接影响语图最核心的差异化指标。

### R3 · 通用导出体系

**功能点描述**
提供统一的「导出」入口，从**同一份 FlowDraft + 布局结果**派生多种目标格式，分三档能力：
- **档一 · 位图与矢量**：PNG（可选倍率与透明底）、SVG（文本可编辑、字体内嵌或转路径）、PDF（自动分页与图框适配）。
- **档二 · 可再编辑的图形工程文件**：**Mermaid 代码**（`.mmd`，与 R4 导入构成双向闭环）、**draw.io XML**（`.drawio` / `.xml`，遵循 `mxfile` 结构，可被 draw.io 直接打开继续编辑）。
- **档三 · 办公文档**：**可编辑 PPTX**（每个节点/连线作为独立可编辑形状而非整图贴图，对齐 Napkin 的核心卖点）、可选 Visio `.vsdx`（对齐 EdrawMax / GitMind，作为国内企业客户的硬需求）。
附带：导出前预览、批量导出（项目内多图一次打包）、导出配置记忆（记住用户上次选的格式与倍率）。

**用户价值**
导出是**图形产品的「出口」，没有出口就没有价值兑现**。用户画图的终点几乎从来不是「在这个工具里看着」，而是要放进 PPT 汇报、贴进文档、发给同事、或迁到自己更熟悉的工具里继续编辑。当前语图 100% 停在画布内，意味着用户必须截图 —— 截图不可编辑、放大失真、无法进 PPT 母版，是明显的体验断崖。可编辑 PPTX 尤其关键：它让 AI 生成的图直接变成用户汇报材料的一部分，把语图从「画图工具」变成「汇报生产力工具」。提供 draw.io XML / Mermaid 导出还传递一个强信号 —— **不锁定用户**，降低试用心理门槛。

**实现难度评估：中**
- 理由：档一（PNG/SVG/PDF）难度低，X6 自带画布导出能力，主要工作是分辨率、字体、边界裁剪与分页的工程细节。档二难度中：Mermaid 导出是纯映射（FlowDraft 的 `type` → Mermaid 图形语法，`label` → 文本，边 → 箭头），几乎无风险；draw.io XML 导出需要构造合法的 `mxfile`/`mxCell` 结构与样式串，可参照 draw.io 官方公开的 `mxfile.xsd` 与 Style Reference 保证合法性。档三难度中高：PPTX 需要用 Office Open XML 生成可编辑形状（可引入成熟的纯 JS PPTX 生成库，属应用层依赖而非基础设施依赖），Visio `.vsdx` 格式最复杂、生态库最少，建议作为可选后置项。整体是「工程量集中但技术风险低」的类型，且**完全没有 AI 不确定性** —— 是确定性收益。
- 依赖的现有模块：**A2 FlowDraft**（所有导出器的统一输入源，语义/呈现解耦使导出器不必理解模型输出）、**A4 程序化自动布局**（导出时的排版归一化：先跑一遍布局再导出，保证导出结果与画布一致且无重叠）、**A3 NODE_TYPE_CONFIG**（每种语义节点在各目标格式里的形状映射表）、**A9 工具适配层**（导出服务若走后端异步生成，可作为工具挂载，复用结果归一化与结构化错误）、**A8 SSE**（批量导出的进度反馈）。

**预期收益说明**
- 补齐 G5 这一**生存性缺口**（全矩阵 15/15 产品均具备导出，语图为 0），消除最容易被用户当作「不成熟」的证据。
- 可编辑 PPTX 是**可直接对外传播的差异化卖点**：在国内市场仅 Napkin（信息图方向）与 EdrawMax 提供，流程图方向的 AI 产品普遍只做图片导出。
- 与 R4 配对后形成 **Mermaid / draw.io 双向闭环**，把语图接入既有图表生态的存量用户池（Mermaid 与 draw.io 的用户基数极大且多为技术决策者）。
- 导出行为是天然的**传播与转化埋点**（导出的文件带来源标识即自传播），也为用户付费意愿提供明确锚点（高档格式如 PPTX/Visio 可作为付费点，衔接 R13）。

**与现有能力的衔接点**
A2（统一数据契约，一次实现多格式派生）、A4（布局归一化）、A3（形状映射表）、A9（后端异步导出挂载点）、A8（进度反馈）、A15 Token 三级防护（导出本身不耗 Token，但可作为额度体系的差异化权益维度，衔接 R13）。**不引入基础设施依赖**，仅引入应用层文档生成库。

**落地优先级：P0**
理由：唯一「竞品 100% 覆盖、语图 0% 覆盖、且技术风险低、无 AI 不确定性」的缺口。档一 + Mermaid 导出可以极小成本先上线止血，档二/档三渐进补齐。

### R4 · Mermaid / draw.io 导入 + AI 语法修复

**功能点描述**
提供「导入」入口，支持三类来源转为语图原生可编辑图谱：
1. **Mermaid 代码**（粘贴文本或上传 `.mmd`）→ 解析为 FlowDraft → 走 A4 自动布局 → 渲染为 X6 图。
2. **draw.io 文件**（`.drawio` / `.xml`，含压缩格式）→ 解析 `mxCell` 几何与样式 → 归一化为 FlowDraft。
3. **图片中的 Mermaid 代码 / 纯文本大纲**（衔接 R5 多模态）。

配套 **AI 修复（Diagram Repair）**：导入内容语法错误或不完整时（Mermaid 常见：箭头写法错误、中文标签未加引号、`subgraph` 未闭合、节点 id 与保留字冲突），自动定位错误行、给出修复建议并可一键应用；无法自动修复时明确标出错误位置与原因，而非静默失败或整体拒绝。导入后**完整保留增量修改能力** —— 导入的图与 AI 生成的图在四级匹配面前地位等同，可以继续用自然语言改。

**用户价值**
解决**迁移成本**这一新用户转化的最大障碍：用户手里已有大量存量 Mermaid 代码（写在 README、技术文档、Notion 里）和 draw.io 文件，如果导入不了，就意味着「换工具 = 全部重画」，几乎必然放弃尝试。AI 修复解决另一个高频痛点 —— Mermaid 语法门槛看似低但**极易出错且报错信息晦涩**（这是 Mermaid Chart 专门做 Diagram Repair、Excalidraw 专门做 AI Repair 的原因，说明该痛点已被市场验证）。「导入后还能继续用自然语言改」则是关键增值：它把语图定位为**存量图的 AI 增强层**，而不是又一个竞争性的画图工具 —— 这个定位比「从零生成」更容易被已有工作流的用户接受。

**实现难度评估：中**
- 理由：Mermaid 解析难度低 —— 语图只需支持流程图相关子集（`graph`/`flowchart` 语法），且社区有成熟的开源解析库可直接用，Excalidraw 的 `@excalidraw/mermaid-to-excalidraw` 已验证「Mermaid → 画布图形」这条路径的可行性与工程范式，可直接参照其映射策略。draw.io XML 解析难度中 —— `mxfile` 结构公开且有官方 `mxfile.xsd`，主要工作量在处理压缩编码、样式串解析、以及**几何坐标到语义类型的反向推断**（draw.io 里只有形状样式没有语义 type，需要从形状/样式反推 `start`/`process`/`decision`/`io`/`subprocess`，存在歧义）。AI 修复难度低 —— 本质是把错误信息喂给模型做局部修正，语图的 Rewriter 已经是同一套机制。风险点：draw.io 导入的语义反推准确率需要评估集兜底，建议初期对无法确定语义的形状统一降级为 `process` 并允许用户批量改类型。
- 依赖的现有模块：**A2 FlowDraft**（导入的目标格式，导入器 = 解析器 + FlowDraft 构造器）、**A6 反思校验 + Rewriter**（导入内容的结构校验与 AI 修复，7 类校验规则可直接复用于校验导入结果合法性）、**A4 程序化自动布局**（导入后重排，Mermaid 本身不含布局信息，必须靠 A4）、**A5 四级匹配**（导入图后续增量修改的引擎）、**A9 工具适配层**（导入解析器作为工具挂载，复用入口 Zod 校验、结果封顶与分级重试）、**A3 NODE_TYPE_CONFIG**（语义类型 ↔ 目标格式的映射表，与 R3 导出共用同一张表）。

**预期收益说明**
- 与 R3 配对形成**双向闭环**，把语图从「孤立的 AI 画图工具」变成「图形生态的枢纽」，接入 Mermaid 与 draw.io 两个最大的存量用户池。
- 导入路径的用户是**已有明确需求的专业用户**，转化质量与留存显著高于「随手试试生成」的用户。
- AI 修复能力可与语图已有的反思校验合并表达为统一的**「图形质量守门人」**能力，对外形成一致的技术叙事（竞品只做语法修复，语图做语法 + 结构语义双层修复）。
- 导入功能同时是 R5（多模态输入）的技术铺垫：图片转图 = 图片 → Mermaid/中间描述 → 走同一套导入管线。

**与现有能力的衔接点**
A2（统一目标格式）、A6（校验 + Rewriter 复用为修复引擎）、A4（导入后布局）、A5（导入后增量修改）、A9（解析器挂载点）、A3（与 R3 共用映射表，双向对称）。**不引入基础设施依赖**，Mermaid 解析库属应用层依赖。

**落地优先级：P0**
理由：与 R3 是同一枚硬币的两面，应配对交付（至少 Mermaid 双向要先通）。迁移成本是新用户转化的硬门槛，且技术风险低、路径已被 Excalidraw / Mermaid Chart 验证。draw.io 导入可作为 R3/R4 之后的紧随项。

### R5 · 多模态输入（截图 / 照片 / 草图 / 文档 / 链接）

**功能点描述**
把输入面从「纯文本」扩展到四类：
1. **图片转可编辑图**：上传白板照片、手绘草图、他人分享的流程图截图 → 识别节点、连线、文字标签与图形类型 → 生成 FlowDraft → 渲染为**可继续编辑、可继续用自然语言改**的语图原生图（不是贴图）。低置信识别结果进入人在回路确认（「这个形状是判断节点还是处理节点？」）。
2. **文档理解**：上传 PRD、技术方案、会议纪要、论文（Markdown / Word / PDF / HTML）→ 抽取其中描述的流程 → 生成流程图；支持「只根据第 3 节的审批流程画图」这类局部指令。
3. **链接抓取**：粘贴 URL → 抓取正文 → 抽取流程。
4. **截图带指令**：截图 + 自然语言（「按这张图的结构，但把支付环节改成先风控后扣款」）→ 参考图 + 修改意图联合处理。

**用户价值**
这是 **2026 年国内 AI 图形产品的主战场**：ProcessOn AI 3.0 主打「图片还原为可编辑图形 + 资料理解（文档/论文/纪要/截图）」，EdrawMax 主打「拍照转图 / 草图秒变电子版」，GitMind 支持「文字/文件/链接/图片/音视频」五路输入，Eraser 支持「图片转可编辑」，Napkin 支持导入 PPT/Word/PDF/HTML/MD。市场已经教育出明确预期：**AI 图形工具应该能吃进我手边已有的任何形态的信息**。对语图的具体价值在于两个高频真实场景 —— ①「同事发我一张流程图截图，我要改它」（目前只能照着重画，是最痛的场景之一）；②「我有一篇 PRD，我要把里面的流程画出来」（目前只能自己读完再手动描述给 AI，信息损耗大）。这两类场景的共同点是**信息来源已在别处存在**，多模态直接消除「人肉转录」这一最枯燥的环节。

**实现难度评估：高**
- 理由：难度分三层且逐层升高。①**图片识别层**最难：需要多模态模型理解图形语义（不只是 OCR 文字），箭头方向、连线归属、形状类型判定都容易出错，尤其手绘草图与低质量照片；且识别结果是「图结构」这种强约束输出，错误不像文本那样可容忍。②**文档理解层**中等：需要文档解析（PDF/Word 版面还原）+ 长文本中流程信息的抽取，语图的上下文分段预算机制可以承接，但「文档里哪段是流程」的判定本身有歧义。③**链接抓取层**最轻：主要是抓取与正文提取的工程问题，但涉及外部网络调用的稳定性与合规（robots、内容授权）。整体还需要处理：文件大小与格式白名单、恶意文件防护、图片中嵌入的 Prompt 注入（**多模态注入是新增攻击面**）、以及识别失败时的降级话术。风险最高的一环是**识别准确率不达预期时的体验崩塌** —— 用户拿到一张错漏百出的图，比没有这个功能更糟。
- 依赖的现有模块：**A9 工具调用适配层**（图片识别、文档解析、URL 抓取各自作为工具挂载，直接复用白名单、入口 Zod 校验、结果封顶 top-K + 字段白名单、结构化错误、分级重试 network ≤3 / param ≤3 —— 多模态调用天然不稳定，这套重试机制正是为它准备的）、**A2 FlowDraft**（识别结果的统一目标格式，模型仍然只输出语义不输出坐标）、**A6 反思校验**（识别出的图结构必须过 7 类结构校验 + 环检测，过滤明显错误）、**A7 人在回路**（低置信形状类型/连线归属走 `need_confirm` + `candidates` 确认，`resumeToken` 保证续跑）、**A8 SSE**（图片识别与长文档解析都是长任务，需要「思考流式」进度反馈）、**A16 Prompt 注入防御**（需扩展为覆盖图片内嵌文本的多模态注入）、**A15 Token 三级防护**（多模态调用的 Token 成本远高于纯文本，配额必须先生效）、**A4 自动布局**（识别结果无可靠坐标，必须重排）、**A5 四级匹配**（「截图 + 修改指令」场景中，参考图与目标图的节点对齐）、R4 导入管线（图片 → Mermaid/中间描述 → 复用导入路径）。

**预期收益说明**
- 补齐 G3，与国内外主流产品的输入能力对齐，消除「只能打字」这一显眼短板，直接进入 2026 年国内产品的主竞争维度。
- 「截图改图」是**竞品少有能力做到「可编辑 + 可继续自然语言迭代」的场景** —— 多数产品止步于「图片转静态图」，而语图的四级匹配使得转换后的图能被持续迭代，这是可对外表达的差异化。
- 多模态输入的 Token 成本显著更高，会直接推高单用户成本，因此与 R13（额度产品面）**必须同期或先行**，否则是纯成本敞口。
- 风险与收益并存：这是 14 条建议中**唯一「做不好会伤害产品口碑」**的一项，因此建议以「文档理解 + 链接」先行（难度较低、准确率可控），「图片转图」在识别准确率经 A12 评估集验证达标后再对外开放。

**与现有能力的衔接点**
A9（三类解析器的统一挂载点，重试与封顶机制正是多模态所需）、A2（识别结果落 FlowDraft）、A6（结构校验过滤错误识别）、A7（低置信确认）、A8（长任务进度）、A16（需扩展多模态注入防御）、A15（成本控制前置条件）、A4/A5（布局与后续迭代）、R4（导入管线复用）。

**落地优先级：P1**
理由：价值高、竞品压力大，但**实现难度为全清单最高、且存在口碑反噬风险**，不宜与 R1–R4 同期铺开。建议排在 P0 五项之后，以「文档 + 链接」为第一阶段、「图片转图」为第二阶段，且第二阶段需以 A12 评估集的识别准确率闸门为放量前提。同时 R13（额度）应先行，避免成本失控。

### R6 · 多图表类型扩展（时序图 / ER 图 / 架构图 / 思维导图）

**功能点描述**
在现有流程图之外，按优先级逐个扩展图型，每种图型都是「一套新的语义节点 CONFIG + 一套新的布局策略 + 一套意图识别规则」的组合：
1. **时序图（Sequence）**：参与者 + 消息 + 生命线 + 同步/异步/返回 + 可选 `alt`/`loop` 片段。技术团队高频需求。
2. **思维导图（Mind Map）**：中心主题 + 多级分支，支持 AI **续写扩枝**（「再给我 5 个方向」）。门槛最低、传播性最强。
3. **ER 图**：实体 + 字段 + 关系基数（1:1 / 1:N / M:N）。
4. **架构图 / 云架构图**：分层容器（客户端 / 网关 / 服务 / 数据 / 外部）+ 组件 + 常见云服务图标语义。
5. **甘特图 / 时间线**（可选，GitMind 已覆盖）。
关键约束：**FlowDraft 语义/呈现解耦的架构不变** —— 新图型是新增 `type` 枚举与新增 CONFIG，而不是另起一套数据结构。跨图型转换作为增值能力（「把这个流程图转成时序图」）。

**用户价值**
单一流程图严重限制产品的适用人群与使用频次。技术团队画架构图与时序图、产品团队画思维导图、数据团队画 ER 图 —— 每多一种图型就多进入一个工种的工作流。市场已经形成明确对标：Mermaid Chart 支持 17 种图型、EdrawMax 号称 210 种（AI 可生成 50+）、Miro 覆盖 BPMN/UML/ERD/AWS/Azure/GCP/K8s、Eraser 覆盖 5 类、GitMind 主打「AI 图表全家桶」。**「只会画流程图」在这个矩阵里显得能力单薄**。此外，思维导图是最容易被非技术用户理解和传播的图型，是拉新的天然入口（GitMind 正是以思维导图起家扩展到全家桶）。

**实现难度评估：中**
- 理由：架构上**已经为扩展预留好了口子** —— A3 的 `NODE_TYPE_CONFIG` 与 `PORT_GROUPS` 是配置化的，A2 的 FlowDraft 不含呈现细节，因此新增图型不需要改动核心链路。真正的成本在于：①**每种图型的布局算法都要单独设计**（时序图是「参与者横排 + 消息按时间纵排」，与流程图的最长路径分层完全不同；思维导图是径向/横向树布局；ER 图需要避免关系线交叉）—— A4 目前只有流程图布局，需要抽象为「布局策略」接口再逐个实现，这是主要工作量。②**意图识别需要区分「用户要哪种图」**，且用户经常不明确说（「画个下单流程」可能要流程图也可能要时序图），需要与 R2 的澄清追问配合。③**Prompt 与评估集要按图型分别维护**，A12 的 52 用例需要成倍扩充。④每种图型的编辑器交互（如时序图拖动消息顺序、思维导图 Tab 键加子节点）需要单独设计。建议按「思维导图 → 时序图 → ER 图 → 架构图」顺序推进，前者布局简单、后者图标语义复杂。
- 依赖的现有模块：**A3 NODE_TYPE_CONFIG + PORT_GROUPS**（每图型一套 CONFIG，扩展点已就位）、**A2 FlowDraft**（数据契约不变，仅扩 `type` 枚举）、**A4 程序化自动布局**（需抽象为布局策略接口，是主要改造点）、**A1 意图识别**（新增图型选择维度，规则优先 + LLM 兜底的框架可复用）、**A6 反思校验**（每图型的结构校验规则不同，如时序图需校验消息必须有收发双方、思维导图需校验单根连通）、**A10 TemplateMatcher**（每图型配套模板）、**A12 回归评估**（用例集按图型扩充）、R3/R4（导出导入需按图型分别支持，Mermaid 天然覆盖时序/ER/思维导图/甘特，是优先扩展 Mermaid 双向的理由）。

**预期收益说明**
- 直接扩大目标用户面（从「画流程图的人」到「需要把想法可视化的人」）与使用频次（同一用户在不同场景调用不同图型）。
- **思维导图是低成本高传播的拉新入口**，且其布局（树）是所有布局里最简单的，可作为多图表类型架构改造的首个验证载体。
- 时序图与 ER 图切入技术团队的核心工作流，与 R10（MCP）、R11（代码库/数据源驱动）形成协同 —— 技术用户是最可能通过 MCP 集成的群体。
- 多图型让 R7（模板中心）的模板数量有了自然的增长维度（每图型 × 每行业场景），是模板生态的前提。
- 风险：图型铺得太快会稀释每种图型的打磨深度，ProcessOn 明确提到「分类型专业图形打磨」是其投入重点，说明**深度比广度更能形成口碑**。建议单图型做到「可日常使用」再启下一个。

**与现有能力的衔接点**
A3（CONFIG 化扩展点）、A2（契约不变）、A4（需抽象为布局策略接口）、A1（意图扩枚举 + 补规则 + 补 Prompt）、A6（按图型分校验规则）、A10（模板配套）、A12（评估集扩充）、R2（图型歧义走澄清追问）、R3/R4（Mermaid 天然多图型，双向闭环优先做 Mermaid 支持的图型）。

**落地优先级：P1**
理由：价值明确且架构已预留扩展点，但**每种图型都是独立的布局 + 校验 + Prompt + 评估集 + 交互的完整工程**，总量大且无法与 P0 并行。建议在 P0 五项稳定后启动，首推思维导图（布局最简单、拉新价值最高），其次时序图（技术用户刚需、Mermaid 支持成熟）。

### R7 · 模板中心产品面（可见、可搜、可一键同款）

**功能点描述**
把后端已有的 `TemplateMatcher` 短路能力**做成用户看得见、选得着的产品面**：
1. **模板画廊**：分类浏览（按场景：审批流 / 电商下单 / 用户注册登录 / CI-CD / 故障处理 / 请假报销；按行业：金融 / 医疗 / 制造 / 互联网；按图型），每个模板带缩略预览图与一句话说明。
2. **模板搜索**：关键词搜索模板，复用现有 PG `tsvector` + GIN 全文检索（与 Ctrl+K 同一套能力）。
3. **一键同款**：看到别人分享的图或官方模板，一键套用其结构与样式，替换为自己的内容（对齐 EdrawMax「一键同款」）。
4. **AI 生成结果沉淀为模板**：用户对某次 AI 生成结果满意，可「保存为我的模板」，下次同类需求直接命中、不走 LLM。
5. **对话中主动推荐**：当用户描述与某模板高度相似时，AI 浮窗提示「检测到你可能在画『订单审批流程』，是否使用模板？」，用户可选择模板起步再迭代。

**用户价值**
解决**冷启动的空白画布恐惧**与**「AI 生成不稳定」的双重焦虑**。面对空白画布，多数用户不知道从何说起；而直接让 AI 生成，结果质量又有波动。模板提供了「确定性起点」—— 用户从一个专业、完整、排版好的模板出发，再用自然语言做增量修改，把 AI 的角色从「凭空创作」降级为「按需调整」，成功率和满意度都显著更高。Miro 有 6000+ 模板、EdrawMax 有 7 万+ 模板与 1.7 万+ 符号、Whimsical 与 GitMind 也都以模板库为核心获客资产，说明**模板是图形产品的标配基础设施，而非增值功能**。此外，「AI 结果沉淀为我的模板」这一条把用户的高满意时刻转化为可复用资产，形成正向飞轮：用得越多 → 私有模板越多 → 命中短路越多 → 响应更快、成本更低、质量更稳。

**实现难度评估：低**
- 理由：这是全清单中**投入产出比最高的一项** —— 后端能力（`TemplateMatcher` 模板匹配短路）已经存在并在跑，缺的只是前端产品面与数据运营。技术工作主要是：模板列表/详情/预览的 CRUD 接口、缩略图生成（可复用 R3 的导出能力批量生成）、画廊 UI、搜索（**直接复用现成的 tsvector + GIN 索引，无需新建检索基础设施**）、「保存为模板」的写入路径（把当前 FlowDraft + 主题存为模板记录）、推荐触发逻辑（在 TemplateMatcher 命中时不只短路返回，还回传「命中了哪个模板」供前端提示）。真正的工作量在**内容侧而非技术侧** —— 需要设计与维护一批高质量模板。因此建议先做「小而精」：20–30 个覆盖最高频场景的官方模板，配合「用户可自建模板」机制让内容自增长，而不是一上来堆数量。
- 依赖的现有模块：**A10 TemplateMatcher**（核心能力已存在，是现成的后端入口）、**A16 PG `tsvector` + GIN 全文检索**（模板搜索直接复用，不新建检索栈）、**A2 FlowDraft**（模板的存储格式）、**A3 NODE_TYPE_CONFIG**（模板缩略渲染）、R3 导出（批量生成模板缩略图）、R8 主题系统（模板可绑定主题）、**A12 trace**（统计模板命中率与转化率）、**A13 鉴权与 projectId 归属**（区分官方模板 / 项目私有模板 / 用户个人模板的可见性）。

**预期收益说明**
- **命中模板即短路，不调 LLM** —— 直接降低 Token 成本与响应延迟，是全清单中**唯一能同时改善成本和性能**的建议，与 R13 额度体系形成正向关系（模板命中不消耗额度，可作为鼓励用户用模板的机制设计）。
- 提高首次使用成功率：新用户从模板起步的完成率远高于从空白画布起步，直接影响激活率与留存。
- 「保存为我的模板」形成**用户私有资产沉淀**，是提升迁移成本与留存的有效手段（用户的模板库越厚，越不愿意离开）。
- 模板库是 R6（多图型）的内容承载体，也是 R8（主题）的展示载体，三者协同构成「模板生态」维度。
- 官方模板 + 一键同款具备**内容营销与 SEO 价值**（模板页是天然的可索引落地页），Miro / Whimsical / GitMind 均以此获客。

**与现有能力的衔接点**
A10（后端能力已就绪，本条是纯产品化）、A16（检索基础设施现成复用，符合「不引入新依赖」原则）、A2/A3（存储与渲染）、A12（命中率埋点）、A13（可见性与归属）、R3（缩略图）、R8（主题绑定）。**技术风险最低的一条建议。**

**落地优先级：P1**
理由：难度低、收益面广（激活率 + 成本 + 性能 + 留存 + 获客五个方向同时受益），且后端能力已存在，属「摘低垂果实」。之所以未列 P0，是因为它依赖 R3（缩略图导出）与 R8（主题）才能做出完整体验，且不涉及生存性缺口；建议在 P0 交付后立即启动，是与 R8 打包交付的最佳组合。

### R8 · 主题与品牌样式系统

**功能点描述**
在 FlowDraft「语义层」之上引入独立的「样式层」，两者正交：
1. **内置主题**：提供 4–6 套预设主题（对齐 Mermaid Chart 的 4 主题），如「经典黑白（打印友好）」「商务蓝」「柔和多彩」「深色模式」「手绘风（对齐 Excalidraw 气质）」。一键切换，全图即时重渲染，**图形语义与结构完全不变**。
2. **品牌自定义**：企业用户可定义品牌主题 —— 主色/辅色、字体、线宽、圆角、节点填充与描边规则、决策节点强调色。保存后可在项目/团队级别统一应用（对齐 Napkin Brand Studio、Miro/Lucid 品牌套件）。
3. **按语义类型着色规则**：可配置「start/end 用某色、decision 用某色、异常分支用红色」等规则，支持**条件着色**（如「所有标签含『失败』的节点标红」，对齐 Lucid 的条件格式化）。
4. **AI 感知主题**：用户可用自然语言改样式（「整体换成深色科技风」「把审批相关的节点都标成蓝色」），AI 输出的是主题/样式指令而非逐节点坐标，走同一套 FlowDraft 语义通道。

**用户价值**
解决**「AI 生成的图很丑 / 不像我们公司风格」**这一影响实际采用的关键问题。技术上正确的图，如果配色刺眼、字体不统一、放进公司 PPT 格格不入，用户就不会真的用它 —— 会转而手动重画。Whimsical 把「约束式美学设计」作为核心卖点（自动布局天然整齐），Napkin 专门做 Brand Studio，说明**视觉品质是这类产品的硬需求而非锦上添花**。对语图还有一个结构性好处：因为 FlowDraft 已经把语义与呈现彻底解耦（模型不输出样式），主题系统是**架构上零冲突的自然延伸** —— 用户切换主题不需要重新调用 AI，是纯前端渲染层的操作，这意味着「样式满意度」问题可以**完全不消耗 Token** 地解决。深色模式则是长时间使用的基础体验。

**实现难度评估：低**
- 理由：语图的架构对这项功能异常友好 —— 样式本来就集中在 `NODE_TYPE_CONFIG` 里而非散落在模型输出中，因此实现主题本质上是**把 CONFIG 里的硬编码样式抽成可切换的主题变量表**，再在 X6 渲染时按当前主题解析。工作量集中在：①样式变量的抽取与主题 schema 设计；②主题切换时的全图重渲染与性能（大图需要批量更新而非逐节点）；③边样式、端口、箭头、文字换行的主题化（容易漏）；④深色模式的对比度校准。品牌自定义与条件着色规则稍复杂，需要规则引擎与优先级判定，但可以后置。风险很低，因为不涉及 AI 不确定性，也不涉及数据迁移（样式不入库、只存主题 id）。
- 依赖的现有模块：**A3 NODE_TYPE_CONFIG**（样式抽取的唯一来源，是主要改造点）、**A2 FlowDraft**（语义层不变，是主题可切换的架构前提 —— 这是语图相对 diagram-as-code 产品的结构优势，code 类产品改主题要重新生成代码）、**A4 程序化自动布局**（部分主题涉及节点尺寸/间距变化，需要布局参数随主题联动）、前端 X6 渲染层、**A11 记忆体系**（记住用户的主题偏好与品牌设定，跨项目复用）、R7 模板中心（模板可绑定默认主题）。

**预期收益说明**
- 直接提升「生成结果可用率」—— 用户不需要为了好看而手动调整样式，这是导出（R3）能真正被使用的前提（导出一张丑图没人愿意放进 PPT）。
- **零 Token 成本的满意度提升**：主题切换不调模型，与 R7（模板短路）、R13（额度）共同构成成本友好型体验。
- 品牌主题是**企业客户的采购决策项**（Napkin、Miro、Lucid 都以此打企业市场），是 R14 企业版能力包的一部分。
- 深色模式与手绘风具备社区传播属性（Excalidraw 的手绘风是其标志性识别度来源）。
- 与 R7 打包后，「模板 + 主题」共同补齐模板生态维度，构成完整的第一印象体验。

**与现有能力的衔接点**
A3（样式集中地，抽取为主题变量）、A2（语义/呈现解耦是零冲突的根因）、A4（布局参数联动）、A11（主题与品牌偏好记忆）、R7（模板绑定主题）、R3（导出时应用主题）。**不引入任何新依赖。**

**落地优先级：P1**
理由：难度低、见效快、且是 R3 导出真正有价值的前提（导出的图必须好看）。建议与 R7 打包为「模板 + 主题」一批交付，形成完整的第一印象体验闭环。内置 4 套主题可先行，品牌自定义与条件着色后置。

### R9 · 视觉质量自检（布局体检 + 多方案供选）

**功能点描述**
在现有**结构层**反思校验之上，增加**视觉层**自检，并暴露为用户可感知的能力：
1. **布局体检规则集**（确定性算法，不调模型）：节点重叠检测、连线穿越节点检测、连线交叉数统计、标签溢出节点边界检测、孤立节点/孤立子图检测、层级跨度异常检测（连线跨越过多层）、图整体宽高比异常（过宽或过高，不利于阅读与导出）。
2. **体检结果分级**：`error`（必须修，如节点重叠）/ `warning`（建议修，如连线交叉过多）/ `info`（提示，如图偏宽）。与现有环检测的 warning 级语义保持一致。
3. **自动修复**：`error` 级问题触发自动重布局（复用 A4 的碰撞检测与步进偏移）；`warning` 级给出建议但不强制。
4. **多方案供选**：对同一需求，一次生成 **2–3 个布局/结构方案**（如「纵向分层版」「横向泳道版」「精简版」），用户点选一个继续迭代（对齐 Napkin 的「多个视觉方案供选」）。
5. **体检报告可视化**：在画布上直接标出问题位置（红框/黄框 + 悬浮说明），而非只在对话里给一段文字。

**用户价值**
解决 AI 生成图形**最直观、最影响第一印象**的问题：**「结构对但看起来很乱」**。用户判断一个 AI 画图工具好不好用，第一眼看的是排版是否整齐、有没有线条打架、文字有没有溢出 —— 而不是图结构是否语义正确。当前语图的反思校验能保证「结构合法」（无悬空节点、无非法类型、环检测），但**完全不保证「视觉可读」**：一张结构 100% 正确但节点重叠、连线乱穿的图，在用户眼里就是失败的。Whimsical 把「约束式美学」当核心卖点、Lucid 有条件格式化、Napkin 用「多方案供选」把选择权交给用户，都是针对同一痛点。多方案供选还有额外的心理学价值：把「AI 给的结果不满意」转化为「我选哪个」，用户从评判者变成决策者，满意度显著提升。

**实现难度评估：中**
- 理由：体检规则集**难度低于预期**，因为 A4 的自动布局里**已经实现了矩形碰撞检测**，几何计算能力（包围盒、相交判定、间距约束）现成可复用 —— 大部分体检规则只是把布局算法内部的中间判定结果**暴露出来并扩展到边与标签**。连线交叉检测、标签溢出检测是标准计算几何问题。分级与自动修复也已有范式（环检测就是 warning 级 + 不强制修）。真正的复杂度在两点：①**多方案供选**需要布局策略的多样化（当前 A4 只有「最长路径分层 + 先下后右步进」一种策略，要产出有意义的差异方案需要至少 2–3 种布局变体，如横向/纵向/紧凑/宽松），这与 R6 的「布局策略接口抽象」是同一项工作，应合并设计；②**体检报告在画布上的可视化标注**需要 X6 的临时图层管理。风险点：体检规则过严会导致大量图被标红，反而制造焦虑，需要用 A12 评估集校准阈值。
- 依赖的现有模块：**A6 反思校验**（体检规则作为新的校验规则类挂入 Evaluator，与 7 类结构校验并列；`warning` 级语义与环检测一致）、**A4 程序化自动布局**（碰撞检测与几何计算现成复用；自动修复 = 重跑布局；多方案 = 布局策略变体）、**A3 NODE_TYPE_CONFIG**（标签溢出检测需要节点尺寸信息）、**A12 回归评估 + Bad Case 库**（体检规则的阈值校准必须靠评估集，且「视觉质量」应作为新的评估维度补入四类指标；体检结果本身也是 Bad Case 的自动标注信号）、**A2 FlowDraft**（多方案是同一 FlowDraft 的不同布局结果，语义层不变 —— 又一次受益于解耦架构）、R1 版本快照（用户选定方案后，未选方案可留档）、**A7 人在回路**（多方案选择可复用 `candidates` 卡片机制）。

**预期收益说明**
- **直接提升生成结果的第一印象质量**，这是新用户激活率的决定性因素 —— 用户第一次生成就看到一张排版整齐的图，与看到一张线条打架的图，留存差异巨大。
- 把语图的质量保证从「结构合法」升级为**「结构合法 + 视觉可读」双层**，形成完整的对外技术叙事：竞品（Mermaid Chart Diagram Repair、Excalidraw AI Repair、ProcessOn AI 自查纠错）主要做语法/结构修复，**视觉层自检在公开材料中未见竞品系统化实现**，是可主张的差异化。
- 体检规则是**确定性算法、零 Token 成本**，可以在不调模型的前提下拦截大量低质量输出，与 R7/R8 同属成本友好型质量提升。
- 多方案供选把「不满意 → 重来」变成「选一个 → 迭代」，减少无效重生成，降低 Token 消耗（衔接 R13）。
- 体检结果为 A12 的 Bad Case 库提供**自动化标注信号**，形成「体检发现问题 → 入 Bad Case 库 → 改进 Prompt/布局 → 闸门验证」的质量闭环。

**与现有能力的衔接点**
A6（Evaluator 新增视觉规则类，复用现有 warning 分级与 Rewriter 修正闭环）、A4（碰撞检测与几何计算现成复用，布局策略变体化）、A3（尺寸信息）、A12（阈值校准 + 新增「视觉质量」评估维度 + Bad Case 自动标注）、A2（多方案共享语义层）、A7（多方案选择复用 `candidates`）、R6（布局策略接口抽象应合并设计）、R1（未选方案留档）。

**落地优先级：P0**
理由：这是**唯一直接影响「AI 内核输出质量」这一立身之本**的建议，且大部分几何能力已在 A4 中存在、复用度极高、零 Token 成本。语图的差异化叙事是「生成质量可靠」（反思校验 + 评估闸门），视觉层缺失会让这一叙事在用户第一眼就被证伪。建议在 P0 批次内与 R1 同期推进；其中「体检规则 + 自动重布局」可先行（成本低、见效快），「多方案供选」待 R6 的布局策略接口就绪后跟进。

### R10 · MCP Server 与开放集成

**功能点描述**
把语图的能力**协议化对外暴露**，让其他 AI 工具能调用语图，同时也让语图能接入外部工具：
1. **语图 MCP Server（对外）**：暴露若干工具供 Claude Desktop / Claude Code / Cursor / VS Code 等 MCP 客户端调用 —— `create_diagram`（自然语言 → 图，返回图 id 与可访问链接）、`modify_diagram`（对指定图做增量修改）、`export_diagram`（导出为 Mermaid / SVG / draw.io XML）、`query_diagram`（咨询图结构，返回文字说明）、`list_templates`。
2. **参照 draw.io 的四条集成路径**做梯度覆盖：MCP App Server（远程托管）、npm Tool Server（本地）、IDE 插件（Claude Code / VS Code）、Project Instructions（项目级规则文件）。
3. **IDE 与文档插件**：VS Code / JetBrains 插件（在 IDE 内把选中代码转为架构图/时序图，对齐 Claude Code 读代码库出图的能力）；可选的 Confluence / Notion / 飞书文档嵌入。
4. **公开 API + Webhook**：REST API 供第三方系统集成，Webhook 推送图变更事件。

**用户价值**
**MCP 已成为 2026 年 AI 工具的默认集成面，不接入 MCP ≈ 不存在于 AI 工作流中**。draw.io 官方文档专门写了 Diagram Generation 并提供 4 种 MCP 集成路径、Excalidraw 有 MCP Server、Mermaid Chart 有覆盖 ChatGPT/VS Code/JetBrains/PPT/Word/Confluence/Jira/Google Docs 的插件矩阵、Miro 有 250+ 集成与 Connectors、ProcessOn 已把官方 Skill 接入 Coze/OpenClaw/WorkBuddy。对语图的具体价值有三层：①**技术用户的真实工作流在 IDE 里**，如果能在写代码时一句话把当前模块画成架构图并同步到语图，这是极强的黏性场景；②**被集成即分发** —— 通过 MCP，语图成为其他 AI 产品的图形能力后端，获客成本远低于自建流量；③**降低试用门槛** —— 用户不必离开熟悉的工具就能体验语图的核心能力。

**实现难度评估：中**
- 理由：MCP Server 本身技术难度不高（协议公开、有成熟 SDK，本质是给已有能力套一层协议适配）。语图的**A9 工具调用适配层已经把「工具」这套抽象完整实现了** —— 白名单、入口 Zod 校验、结果归一化、结构化错误、结果封顶、分级重试 —— MCP Server 只是把「语图调用外部工具」的方向反过来，变成「外部调用语图能力」，抽象是同一套。真正的复杂度在：①**鉴权模型需要重新设计** —— MCP 客户端是第三方进程，现有 JWT + projectId 归属校验面向自有前端，对外暴露需要 API Key / OAuth 授权流、更细的权限粒度（只读 vs 可写 vs 可删）、以及**速率限制与配额**（衔接 R13）；②**输出契约要面向异构消费者**，返回给 MCP 客户端的结果需要既有机读结构又有可读链接；③**IDE 插件是独立工程**（VS Code / JetBrains 各有技术栈），成本不低，建议后置或先只做 MCP；④对外暴露扩大了攻击面，A16 的 Prompt 注入防御需要覆盖「来自 MCP 客户端的不可信指令」。建议路径：先做 MCP Server（覆盖 create/modify/export/query 四个核心工具），验证需求后再投入 IDE 插件。
- 依赖的现有模块：**A9 工具调用适配层**（工具抽象、白名单、Zod 校验、结果封顶与字段白名单、结构化错误、分级重试全部可直接复用，是本条最大的衔接资产）、**A13 JWT 鉴权与 projectId 归属校验**（需扩展为 API Key / OAuth，403 不泄露存在性的安全语义可延续）、**A15 Token 三级防护**（对外调用必须有配额，否则是开放的成本敞口）、**A8 SSE 协议**（MCP 的流式/进度语义可映射）、R3 导出（`export_diagram` 工具的实现基础）、R4 导入（`create_diagram` 可支持传入 Mermaid）、**A16 Prompt 注入防御**（需覆盖外部不可信指令）、**A12 trace**（对外调用必须有独立的可观测性与审计，衔接 R14）、**A1 意图识别**（对外调用同样走意图路由）。

**预期收益说明**
- 打开**「被集成」这条零边际成本的分发渠道**：Mermaid Chart 的插件矩阵与 ProcessOn 的 Skill 接入 Coze/OpenClaw/WorkBuddy 都证明，插件生态是中小图形产品对抗 Miro/Lucid 这类平台型玩家的有效路径。
- 切入技术用户核心工作流（IDE 内出图），这批用户是**付费意愿与传播力最强的群体**，也是 R6（时序图/ER 图/架构图）与 R11（代码库驱动）的目标用户。
- MCP 的存在让语图从「一个网站」升级为「一项可被编排的能力」，在 AI Agent 生态里的战略位置完全不同。
- 与 draw.io 对标尤其有意义：draw.io 是 Apache 2.0 免费开源，语图无法在价格上竞争，但可以在**「AI 原生的增量修改能力」**上形成差异 —— draw.io 的 MCP 是让 AI 生成 XML，语图的 MCP 是让 AI 做语义级增量修改（四级匹配），后者的能力层级更高。
- 风险：对外 API 的运维、鉴权、配额、滥用防护成本会持续存在，需要 R13/R14 先行或同期。

**与现有能力的衔接点**
A9（工具抽象的完整复用，是本条的核心衔接资产）、A13（鉴权扩展）、A15（配额前置）、A8（流式语义映射）、A16（外部不可信指令防御）、A12（对外调用的可观测性与审计）、A1（意图路由复用）、R3/R4（导出导入能力作为 MCP 工具的实现基础）、R13/R14（额度与合规是对外开放的前提）。

**落地优先级：P1**
理由：战略价值高、且 A9 让技术门槛显著降低，但**它依赖 R3/R4（导出导入）才有完整的工具集，依赖 R13/R14（额度与合规）才能安全对外开放**，因此不宜早于 P0。建议在 R3/R4 交付后启动，先做最小 MCP Server（四个核心工具 + API Key 鉴权 + 配额），验证被集成的真实需求后再决定是否投入 IDE 插件。

### R11 · 数据驱动图（数据源 / 代码库 → 图）

**功能点描述**
让图不再只是「画出来的」，而是「从真实数据生成的」，并保持同步：
1. **代码库 → 架构图 / 时序图 / ER 图**：接入 Git 仓库（对齐 Eraser 的 GitHub 集成、Claude Code 读代码库出架构图），分析模块依赖、调用链、数据模型，生成对应图型；代码变更后支持增量更新（「重新同步」）。
2. **结构化数据 → ER 图**：上传 SQL DDL / CSV / 数据库 schema 快照 → 生成 ER 图。
3. **CSV / JSON → 批量图形**：表格数据批量生成节点（如「把这 50 个微服务按依赖关系画出来」）。
4. **业务系统数据链接**：可选地连接项目管理/工单系统，让流程图节点携带真实状态（对齐 Visio 数据链接图 + Power BI、Lucid Data Linking、Miro Connectors 接 Slack/GitHub/Amplitude）。
5. **数据变更 → 图更新提示**：数据源变化时提示「上游 schema 有 3 处变更，是否同步到图？」。

**用户价值**
解决**「图与现实脱节」**这一专业图表领域最顽固的痛点：架构图画完就过期，没人维护，最后没人信。Visio 的数据链接图、Lucid 的 Data Linking、Miro 的 Connectors、Eraser 的 GitHub 集成、Claude Code 读代码库出图，全部指向同一个价值主张 —— **让图成为数据的视图而非人工的快照**。对语图的具体价值：①技术团队的架构图/ER 图需求本质上是「从代码里长出来的」，手工画既慢又不准；②「代码变更 → 图自动同步」如果做成，就把语图从「一次性画图工具」变成「持续运行的文档基础设施」，黏性与付费理由完全不同层级；③这也是 AI 相对传统图表工具的**结构性优势场景** —— 传统工具做不到语义级理解代码，AI 可以。

**实现难度评估：高**
- 理由：这是全清单**技术复杂度第二高**的一条（仅次于 R5）。难点：①**代码库理解本身就是硬问题** —— 大型仓库的依赖分析、调用链提取、模块边界识别需要静态分析能力，纯靠 LLM 读代码在规模上不可行（Token 与上下文都撑不住），需要「确定性静态分析 + LLM 语义归纳」的混合方案；②**增量同步**需要把代码结构的变化映射为图的变化，这正好可以落到 A5 四级匹配上，但「代码里的哪个模块对应图里的哪个节点」的稳定 id 映射是个需要专门设计的难题；③**外部系统接入的工程量与运维成本**（OAuth、API 限流、Webhook、凭证安全存储）都很重，且每接一个数据源都是一份长期维护负担；④**数据源凭证的安全与合规风险高**（涉及用户代码资产，一旦泄露是致命事件），需要 R14 先行。建议严格收敛范围：先做「上传 SQL DDL → ER 图」与「上传 CSV/JSON → 批量节点」这两个**无需外部集成、无凭证风险**的确定性子集，Git 仓库接入作为中期目标，业务系统数据链接作为长期可选。
- 依赖的现有模块：**A9 工具调用适配层**（数据源接入的标准挂载点 —— 白名单、入口 Zod 校验、结果封顶 top-K + 字段白名单、结构化错误、分级重试 network ≤3 / param ≤3 正是为外部不稳定调用设计的，**结果封顶对代码库这类超大输入尤其关键**）、**A5 四级降级匹配**（增量同步的核心 —— 代码变更映射为图变更，L3 拓扑签名在结构变化场景下特别有用）、**A2 FlowDraft**（分析结果落统一契约）、**A6 反思校验**（生成的图结构校验）、**A11 记忆体系**（数据源快照缓存与变更检测，遗忘曲线可用于过期快照清理）、**A4 自动布局**（大规模节点布局，ER 图与架构图的布局策略）、R6 多图表类型（ER 图/时序图/架构图是本条的载体，**强依赖 R6 先行**）、R10 MCP（Git 接入可复用 MCP 的鉴权与集成范式）、**A15 Token 三级防护**（代码库分析 Token 消耗极高，配额必须先行）、**A13 鉴权与 A14 存储**（数据源凭证的加密存储与归属校验）、R14（合规先行）。

**预期收益说明**
- 切入**最高价值的专业场景**：技术团队的架构图与 ER 图是企业采购图形工具的主要驱动力之一，Visio/Lucid/Miro 的企业营收很大程度建立在这类场景上。
- 「图与代码同步」如果做成，是**极强的护城河与付费理由** —— 公开材料中真正做到「代码变更自动同步到图」的产品极少，Eraser 与 Claude Code 也只做到「从代码生成」而非「持续同步」。
- 数据驱动图的可信度远高于纯 AI 生成图（有真实数据背书），能显著提升语图在专业用户中的口碑。
- 与 R6（ER 图/架构图/时序图）、R10（MCP/Git 集成）形成强协同，共同构成「技术团队工作流」这一完整场景包。
- 风险与成本都很高：外部集成的长期运维负担、代码资产的安全责任、Token 成本的量级跃升。**投入产出比在 14 条中偏低**，因此建议以「无外部依赖的确定性子集」先验证需求，再决定是否投入集成工程。

**与现有能力的衔接点**
A9（数据源挂载点，封顶与重试机制为大规模外部输入而设）、A5（增量同步 = 匹配算法的又一应用场景）、A2（统一契约）、A6（结构校验）、A11（快照缓存与变更检测）、A4（大规模布局）、A15（成本前置）、A13/A14（凭证安全）、R6（图型载体，强前置）、R10（集成范式）、R14（合规前置）。

**落地优先级：P2**
理由：价值高但**难度高、依赖链最长**（强依赖 R6 图型、R10 集成、R13 额度、R14 合规四项先行），且外部集成带来长期运维与安全责任，投入产出比在当前阶段偏低。建议 P2 定位，且**先做无外部依赖的确定性子集**（SQL DDL → ER 图、CSV/JSON → 批量节点）验证需求，Git 仓库与业务系统接入待前置项就绪、需求验证通过后再评估。

### R12 · 轻量实时协作与评论

**功能点描述**
分三级递进引入协作能力，避免一次性做重型协同编辑：
1. **一级 · 分享与只读浏览**：生成项目分享链接（可设密码与有效期），未登录用户可查看图与流程说明，可导出。这是成本最低、价值最直接的一步。
2. **二级 · 评论与标注**：在节点/边上添加评论，支持 @提及、已解决状态；AI 可被 @ 进评论线程（「@语图 这个分支是不是漏了异常处理？」），把评论变成 AI 交互入口（对齐 Napkin 的实时协作 + 评论）。
3. **三级 · 多人实时共同编辑**：多人同时在画布上编辑，光标与选区可见，AI 修改操作对所有人同步；需要处理并发冲突（两人同时改同一节点）。

**用户价值**
协作是**图形产品的团队化门槛**：全矩阵 15 款产品中 12 款具备实时协作（仅 ChatGPT/Claude 与 draw.io 弱），Napkin/Whimsical/Miro/Lucid/Visio/Mermaid Chart/ProcessOn/GitMind 全部支持。图这类产物的天然是「要给别人看、和别人一起改」的 —— 流程评审、方案讨论、交接文档，都发生在多人场景。没有协作能力意味着语图只能是**个人工具**，无法进入团队采购视野，也无法形成「一个人用起来 → 拉同事进来 → 团队付费」的自然增长路径。分享链接（一级）还有额外的传播价值：每个被分享的图都是一次产品曝光。

**实现难度评估：高**
- 理由：三级难度差异极大，必须分开评估。**一级（分享只读）难度低** —— 只是新增一个免鉴权的只读访问路径与链接管理，但要注意安全（现有 A13 的 projectId 归属校验需要扩展为「链接令牌」鉴权模型，且必须避免链接可枚举）。**二级（评论）难度中** —— 新增评论表、@提及通知、以及「AI 进评论线程」需要把评论上下文接入意图识别链路。**三级（实时共同编辑）难度最高** —— 需要 CRDT 或 OT 算法保证多端一致性，需要 WebSocket 长连接基础设施与水平扩展方案（多实例间的消息广播），**并且与 A5 四级匹配产生根本性冲突**：AI 的增量修改假设「一个基线图谱」，多人并发编辑时基线在不断变化，AI 修改的匹配结果可能在应用瞬间就已过期，需要设计「AI 操作 vs 人工操作」的冲突合并策略。此外三级还会带来「多人共享 Token 额度」的计费难题（衔接 R13）。**强烈建议只做一级 + 二级，三级明确不列入当前范围** —— 三级的工程复杂度与语图「不引入重基础设施」的关键决策直接冲突。
- 依赖的现有模块：**A13 JWT 鉴权与 projectId 归属校验**（分享链接需要扩展出「链接令牌」鉴权模型，403 不泄露存在性的安全语义必须延续到分享场景，避免链接枚举攻击）、**A8 SSE**（一级/二级的变更通知可复用现有 SSE 通道，避免为协作新建 WebSocket 基础设施）、**A14 令牌态存储（Redis 可选 / 缺省 PG）**（在线状态与链接令牌可沿用同一套可切换范式，**符合不引入硬依赖原则**）、**A1 意图识别 + A11 记忆**（AI 进评论线程需要把评论上下文并入会话记忆）、**A5 四级匹配**（三级冲突合并的核心，但也是冲突来源）、**A12 trace**（协作操作的审计，衔接 R14）、**A15 Token 三级防护**（多人共享额度的计费模型）、R1 版本快照（协作场景下快照与回滚更加必要，谁改的、改了什么必须可追溯）。

**预期收益说明**
- 一级（分享只读）以**极低成本**解锁「图要给别人看」这一最高频需求，同时带来传播曝光（每个分享链接都是产品入口）。
- 二级（评论 + AI 进线程）是**差异化机会点**：把评论区变成 AI 交互入口，让流程评审中的每条意见都能被 AI 直接响应，这在竞品中未见系统化实现（Napkin 有评论但 AI 不进线程）。
- 打通「个人使用 → 邀请同事 → 团队付费」的增长路径，是从个人工具走向团队产品的必要条件，也是 R14 企业版的前置。
- 三级（实时共同编辑）**收益/成本比在 14 条中最低**：工程量最大、与现有架构冲突最深、与「不引入重基础设施」决策直接矛盾。建议明确不做，或长期观察。

**与现有能力的衔接点**
A13（鉴权模型扩展为链接令牌，安全语义延续）、A8 SSE（复用为变更通知通道，避免新建 WebSocket）、A14（在线状态与链接令牌沿用可切换存储范式）、A1/A11（AI 进评论线程）、A5（三级冲突合并的核心与冲突源）、A12（协作审计）、A15（共享额度）、R1（协作下快照与可追溯性更必要）、R14（企业版前置）。

**落地优先级：P2**
理由：竞品覆盖率高，但**语图当前主线是把 AI 内核能力产品化（R1–R4、R9），协作属于团队化阶段的能力，前置条件是产品已有足够的个人用户价值**。且三级实时协同与规格「不引入新基础设施依赖」的关键决策直接冲突。建议 P2，且**范围严格限定为一级（分享只读）+ 二级（评论 + AI 进线程）**，三级明确排除。一级可作为 P2 内的快速项先行。

### R13 · AI 用量与额度产品面

**功能点描述**
把后端已在生效的 Token 三级防护**变成用户可见、可控、可付费的产品面**：
1. **用量面板**：显示本期已用 / 剩余 AI 额度，按对话/项目/图型维度的用量明细与趋势，高消耗操作提示（如「本次多模态识别消耗 X 额度」）。
2. **额度单位抽象**：把 Token 换算为业务语义单位（对齐 GitMind「算粒」、Napkin「credits」、Whimsical「AI actions」），如「1 次生成 = N 点」、「模板命中 = 0 点」、「主题切换 = 0 点」。
3. **临期与耗尽的优雅降级**：额度不足时提前预警；耗尽后不是硬报错，而是降级到 fast 模型 / 限制单次规模 / 引导使用免费能力（模板、主题、手动编辑、导入导出）。
4. **付费与套餐**：免费额度 + 订阅套餐 + 按量加购；付费权益按能力分层（高档导出格式 PPTX/Visio、多模态输入、多图型、品牌主题、MCP API 调用配额）。
5. **成本可观测（内部）**：按模型/意图/用户维度的真实成本看板，用于模型分层策略调优与定价校准。

**用户价值**
对用户：解决**「不知道还能用多少、突然就不能用了」**的焦虑。当前 Token 三级防护在后端生效，用户撞到配额时只得到一个错误，体验极差且无法转化为付费 —— 因为用户根本不知道自己用掉了什么、为什么用完了、买了能多得什么。可见的额度把「限制」转化为「价值感知」（原来我已经生成了 47 张图）与「付费动机」（还差一点，升级即可）。对运营/产品：没有用量数据就无法定价、无法识别高价值用户、无法评估各功能的真实成本。这一点在多模态（R5）与数据驱动（R11）上线后尤其关键 —— **这两项的单次成本可能是纯文本的 10 倍以上，没有额度产品面就是纯成本敞口**。

**实现难度评估：低**
- 理由：这是与 R7 并列的**最低难度项** —— 配额机制（用户级每日配额、会话级软上限、调用级 `max_tokens`）已经在后端跑，用量数据也已经在 A12 的 trace 里落 PG（按 `threadId`），因此本条主要是**读数与呈现**：新增用量聚合查询与接口、前端面板、额度单位换算规则、耗尽时的降级分支（降级路径本身已有 —— 模型分层策略与 TemplateMatcher 短路都是现成的降级手段）。付费与套餐涉及支付接入与订单系统，是相对独立且标准化的工程，可以后置或外采。内部成本看板只是 trace 数据的另一种聚合视图。风险极低，无 AI 不确定性。
- 依赖的现有模块：**A15 Token 三级防护**（配额即额度，机制已在跑，本条是产品化）、**A12 内置 trace（`threadId` 落 PG）**（用量统计与成本看板的数据源，**无需新建可观测性基础设施**）、**A14 PG 存储范式**（用量聚合表沿用同款写法）、**A16 模型分层策略**（额度耗尽时降级到 fast 模型的现成路径）、**A10 TemplateMatcher**（模板命中不消耗额度，是天然的「免费能力」设计支点）、**A13 鉴权与 projectId 归属**（用量的归属维度）、R3（高档导出格式作为付费权益）、R5（多模态是高消耗项，必须同期）、R10（MCP API 调用配额）、R11（代码库分析的成本控制）、R8（主题切换零 Token，可作为免费能力宣传点）。

**预期收益说明**
- **商业化前置条件**：没有额度产品面就没有定价、没有付费转化。全矩阵产品的商业模式高度一致地采用「AI 额度」维度（Napkin 周 credits、Whimsical AI actions/席位、GitMind 算粒 + ¥19 包月、Miro AI 额度、Lucid 席位 + AI），说明**额度制已是行业标准做法**，语图的机制已就绪，只差产品面。
- **成本止损**：把「撞配额报错」变成「优雅降级」，既保住体验又保住成本上限；用量数据让模型分层策略可以基于真实成本调优。
- **为高成本功能铺路**：R5（多模态）、R11（数据驱动）、R10（对外 API）三项都是成本量级跃升的功能，**R13 必须先行或同期**，否则这三项无法安全放量。
- 用量数据本身是产品洞察来源：哪些图型/意图/功能最耗成本、哪些用户是高价值用户、免费额度定在哪里转化率最高。
- 「模板命中 / 主题切换 / 手动编辑不消耗额度」的设计可以**主动引导用户走向低成本路径**，是产品机制与成本控制的巧妙结合点。

**与现有能力的衔接点**
A15（配额机制已就绪，本条纯产品化）、A12 trace（用量与成本数据源已在 PG，不新建可观测性栈）、A14（存储范式）、A16（模型分层 = 降级路径）、A10（模板短路 = 零额度能力）、A13（归属维度）、R3/R5/R8/R10/R11（权益分层与成本控制对象）。**难度低、依赖少、且是多项高成本功能的前置。**

**落地优先级：P1**
理由：难度低、数据源已就绪，且是 **R5（多模态）、R10（MCP）、R11（数据驱动）三项高成本功能的安全前置**。虽然本身不属生存性缺口，但如果 P1 阶段要启动 R5，则 R13 必须先行。建议在 P1 批次内**排在最前**，用量面板 + 额度单位 + 优雅降级先上，支付与套餐可后置。

### R14 · 企业安全合规与审计

**功能点描述**
构建面向企业客户的信任能力包：
1. **数据留存与使用承诺（明示化）**：在产品与协议中明确写清 —— 用户输入与生成的图**是否用于模型训练**、**留存多久**、**如何删除**（对齐 Lucid 公开承诺「Azure OpenAI 承载、30 天留存、不训练客户数据」）。提供「不留存模式」（会话结束即清除对话与快照）与「一键删除我的全部数据」。
2. **审计日志**：记录谁在何时对哪个项目做了什么（登录、生成、修改、导出、分享、删除、权限变更），支持导出与查询。
3. **SSO / SAML**：企业身份接入（对齐 Whimsical Business、Mermaid Chart Enterprise、Lucid 的 SSO/SAML）。
4. **权限与角色**：项目级角色（所有者 / 编辑者 / 评论者 / 只读），团队与工作区层级。
5. **合规认证路线图**：按目标市场排定 SOC 2 Type II / ISO 27001 / GDPR 的准备（对齐 Eraser SOC II Type 2、EdrawMax GDPR + SOC2 + ISO27001、Lucid FedRAMP）。国内企业客户还需考虑等保与数据本地化。
6. **私有化 / 自托管方案**：把语图「不引入重基础设施」的架构优势转化为商业能力 —— 提供可自托管的部署包（PG + 应用即可跑，Redis/pgvector/ES 均为可选），面向对数据出境敏感的客户。

**用户价值**
合规是企业采购的**前置门槛而非加分项**：没有 SSO 与数据处理协议，企业客户的采购流程根本走不下去。Lucid 把「不训练客户数据 + 30 天留存 + FedRAMP」写进产品页，Eraser 拿 SOC II Type 2，EdrawMax 集齐 GDPR/SOC2/ISO27001 —— 说明**头部产品都把合规作为公开卖点在打**。对语图的特殊价值在于：语图的架构（PG 为唯一硬依赖，Redis 可选，Embedding Provider 可插拔且无 key 可降级，trace 内置不依赖 Langfuse，布局自研不依赖 @antv/layout）天然适合**私有化部署** —— 这是相对 Lucid（绑定 Azure OpenAI）、Miro（重 SaaS 平台）的**结构性差异优势**，但目前完全没有被产品化和对外表达。对国内企业客户，「数据不出内网 + 可接自有模型」的组合极具吸引力。

**实现难度评估：中**
- 理由：六项难度分布不均。**数据留存承诺与一键删除**难度低（主要是策略明确 + 删除路径的完整性，涉及对话、快照、trace、记忆、长期 embedding 各处的级联清除，需要仔细梳理但无技术障碍）。**审计日志**难度低中（A12 的 trace 已经是雏形，需要扩为面向合规的不可篡改审计流并补充非 AI 操作）。**权限与角色**难度中（现有 projectId 归属校验是二元模型，扩为多角色需要贯穿所有接口的鉴权中间件改造）。**SSO/SAML**难度中（协议成熟有库，主要工作在身份映射与会话衔接）。**合规认证**难度高但**主要是流程与组织成本而非技术成本**（需要审计机构、文档体系、控制措施落地，周期长且需要管理层投入）。**私有化部署**难度中（架构已经友好，主要工作是打包、配置外置、离线安装、许可证管理）。建议按「留存承诺 + 一键删除 + 审计日志」→「权限角色 + SSO」→「私有化打包」→「认证」的顺序推进，前两步成本低且立刻可用于企业对话。
- 依赖的现有模块：**A13 JWT 全量鉴权 + projectId 归属校验**（权限角色与 SSO 的扩展基座；403 不泄露资源存在性的安全设计已是良好实践，可延续到审计与分享场景）、**A12 内置 trace（`threadId` 落 PG）**（审计日志的雏形与数据源，**无需引入 Langfuse 等外部可观测性栈**）、**A16 Prompt 注入防御**（安全叙事的一部分；R5 多模态与 R10 MCP 会扩大攻击面，需同步扩展）、**A11 记忆体系**（一键删除必须覆盖滚动摘要、长期记忆、embedding 向量；可插拔 Embedding Provider 的降级设计使「无外部向量服务」的私有化部署成为可能）、**A14 令牌态存储可切换（Redis 可选 / 缺省 PG）**（私有化部署的最小依赖路径已就位）、R1 版本快照（快照也需纳入留存与删除策略）、R12 协作（分享链接的权限模型与审计）、R10 MCP（对外 API 的鉴权、限流与审计）、R13（企业版套餐与合规能力打包销售）。

**预期收益说明**
- **解锁企业客户**：合规是企业采购的前置门槛，直接决定客单价量级（企业席位 vs 个人订阅）。全矩阵中 Lucid、Miro、Visio、EdrawMax、Mermaid Chart Enterprise、Whimsical Business 都以企业版为主要营收来源。
- **私有化部署是语图独有的结构性优势**：「PG 单依赖 + Redis 可选 + Embedding 可降级 + trace 内置 + 布局自研」这套架构，在竞品普遍绑定云厂商 AI 平台（Lucid→Azure OpenAI）或重型 SaaS 的背景下，**是可直接对外主张的差异化卖点**，尤其契合国内数据本地化要求。当前这一优势完全没有被产品化表达，属明显的价值浪费。
- 「不训练客户数据 + 明确留存期 + 一键删除」是**低成本高信任度**的组合 —— Lucid 只是把这些写清楚就形成了竞争力，而语图的机制基础已经存在。
- 审计日志与权限角色同时服务于 R12（协作）与 R10（对外 API）的安全需求，是一项多用的基础投入。
- 风险：合规认证周期长、成本高，且需要持续维护；建议以「客户实际提出的要求」为触发条件按需推进，不预先投入全套认证。

**与现有能力的衔接点**
A13（鉴权与归属是权限角色/SSO 的基座，403 安全语义可延续）、A12 trace（审计日志数据源，不引入外部可观测性栈）、A16（注入防御，需随 R5/R10 扩展攻击面）、A11（一键删除需覆盖摘要/长期记忆/向量；可插拔 Embedding 支撑私有化）、A14（Redis 可选 = 私有化最小依赖路径）、R1/R12/R10/R13（留存策略、协作权限、对外鉴权、企业版打包）。**架构本身已经是合规友好的，本条主要是把既有优势产品化与明示化。**

**落地优先级：P2**
理由：对企业市场是前置门槛，但**当前阶段的主线是把 AI 内核能力产品化并验证个人/小团队价值**，企业销售通道尚未建立时提前投入认证的投入产出比不高。建议 P2，但**「数据留存承诺明示化 + 一键删除 + 审计日志」这三项成本极低且立刻可用于企业对话，建议在 P1 后期就先行**；SSO 与权限角色随首个企业客户需求触发；合规认证按客户实际要求按需推进；私有化部署包作为差异化卖点可在架构稳定后尽早包装。

## 五、落地路线图建议

> 按优先级分批次给出**顺序与依赖关系**，不含时间估计与工期预测。

### 5.1 总体策略：一条主线 + 一条约束

**主线判断**：语图的差距不在 AI 内核（FlowDraft 解耦、四级降级匹配、反思校验 + Rewriter、人在回路、记忆体系、评估闸门在矩阵中属第一梯队，部分领先），而在**「AI 结果如何交付给用户、并进入用户既有工作流」**。因此路线图的主线是 **把已有内核能力产品化 + 打通进出口**，而不是重造 AI 能力。

**硬约束**：全程遵守规格关键决策 —— **不引入新的基础设施硬依赖**（pgvector / Langfuse / Redis / @antv/layout / ES 均不作硬依赖）。本报告 14 条建议经逐项核查**全部满足该约束**：新增存储沿用 PG（快照表、用量表、评论表），可观测性沿用内置 trace，检索沿用 PG `tsvector` + GIN，协作通知沿用 SSE，仅引入应用层库（Mermaid 解析、PPTX 生成）。唯一与该约束存在张力的是 R12 三级（实时共同编辑，需 WebSocket + CRDT），**已明确排除在范围外**。

### 5.2 批次一 · P0：补齐生存性缺口，让核心闭环真正可用

| 顺序 | 建议 | 交付内容 | 关键依赖 |
| --- | --- | --- | --- |
| 1 | **R3 通用导出（档一 + Mermaid）** | PNG / SVG / PDF + Mermaid 代码导出 | A2 FlowDraft、A4 布局、A3 CONFIG |
| 2 | **R9 视觉质量自检（体检 + 自动重布局）** | 布局体检规则集（重叠/穿越/交叉/溢出/孤立/宽高比）+ error 级自动重布局 + 画布标注 | A6 反思校验、A4 碰撞检测、A12 评估集校准 |
| 3 | **R1 版本快照与 Diff / 回滚** | 快照表 + 历史面板 + 色标 diff + 一键回滚 + 逐条拣选回滚 | A5 四级匹配（diff 引擎）、A2、A12 trace |
| 4 | **R2 选区改图 + 澄清追问 + consult 产品面** | 选区进上下文（作 L1 锚点）+ Plan Mode 追问卡片 + consult 结构化呈现与「按此建议修改」 | A7 人在回路、A1 意图识别、A5、A11 |
| 5 | **R4 Mermaid / draw.io 导入 + AI 修复** | Mermaid 导入（与 R3 构成双向）→ draw.io XML 导入 → Diagram Repair | A2、A6 + Rewriter、A4、R3 映射表共用 |

**批次内的顺序理由**
- R3 排在最前：难度低、无 AI 不确定性、竞品 100% 覆盖而语图为 0，属**止血项**；且 R3 的导出能力是 R7 缩略图、R9 多方案预览、R10 MCP `export_diagram` 的公共基础。
- R9 紧随：它直接决定「用户第一眼看到的图好不好看」，而**第一印象决定 R3 导出是否真的被使用**（导出一张排版乱的图没人愿意放进 PPT）。R9 的几何能力大部分已在 A4 中，复用度极高、零 Token 成本。
- R1 在 R2 之前：R1 是 R2 的**安全前提** —— 选区改图会放大 AI 的改动幅度，没有回滚能力就是放大风险。
- R2 在 R1 之后：R2 的选区作为 L1 锚点会拉高四级匹配命中率，是**体验与质量指标的同一杠杆**，效果可用 A12 四类指标验证。
- R4 与 R3 配对收尾：R3 先出（导出）、R4 后入（导入），构成 Mermaid 双向闭环；R4 的 AI 修复直接复用 A6 的 Rewriter 机制。
- **R9 的「多方案供选」子项延后**到 R6 的布局策略接口就绪后再做，因为它需要 2–3 种布局变体才有意义，而当前 A4 只有一种策略。

**批次一的完成标准（可用 A12 评估集量化）**
- 用户能导出可直接使用的图文件（不再是截图）。
- AI 生成结果经过视觉体检，`error` 级问题自动修复后方可呈现。
- 任何一次 AI 修改都可预览 diff、可回滚、可逐条拣选。
- 用户可以「选中几个节点说改这里」，AI 在描述模糊时会先问一句。
- 存量 Mermaid 代码可以导入并继续用自然语言迭代。
- 回归评估集从 52 用例扩充，新增「视觉质量」维度并纳入发版闸门。

### 5.3 批次二 · P1：扩能力面 + 建商业与生态基础

| 顺序 | 建议 | 交付内容 | 关键依赖 |
| --- | --- | --- | --- |
| 1 | **R13 用量与额度产品面** | 用量面板 + 额度单位换算 + 优雅降级 + 内部成本看板（支付套餐后置） | A15 三级防护、A12 trace、A16 模型分层 |
| 2 | **R7 + R8 模板中心 + 主题系统（打包）** | 模板画廊/搜索/一键同款/保存为我的模板/对话内推荐 + 4–6 套内置主题 | A10 TemplateMatcher、A16 全文检索、A3 CONFIG、R3 缩略图 |
| 3 | **R6 多图表类型（先思维导图，再时序图）** | 布局策略接口抽象 + 思维导图（含 AI 扩枝）+ 时序图 | A3 CONFIG、A4（抽象为策略接口，与 R9 多方案共用）、A1、A6、A12 |
| 4 | **R5 多模态输入（先文档 + 链接）** | 文档理解（MD/Word/PDF/HTML）+ URL 抓取 → 生成流程图 | A9 工具适配层、A6、A7、A8、A16（多模态注入）、**R13 先行** |

**批次二的顺序理由**
- **R13 必须排在批次二最前**：它是 R5（多模态）、R10（对外 API）、R11（数据驱动）三项高成本功能的**安全前置**。多模态与代码库分析的单次成本可能是纯文本的 10 倍以上，没有额度产品面就放量等于开成本敞口。R13 难度低、数据源已在 trace 里，先行成本极小。
- **R7 + R8 打包交付**：两者共同补齐「模板生态」维度，且互相成就（模板绑定主题、主题让模板好看）；两项难度均为「低」，是全清单**投入产出比最高的组合**，收益覆盖激活率、成本、性能、留存、获客五个方向。
- **R6 的布局策略接口抽象要与 R9 的「多方案供选」合并设计** —— 这是同一项底层工作，一次抽象同时服务两个功能，避免返工。图型顺序按「布局复杂度递增」：思维导图（树布局，最简单，且是拉新入口）→ 时序图（技术用户刚需，Mermaid 支持成熟，可与 R3/R4 双向闭环）→ ER 图 → 架构图。
- **R5 分两阶段**：本批次只做「文档 + 链接」（难度中、准确率可控）；**「图片转图」延后**，因为它难度最高且存在口碑反噬风险，放量的前置条件是经 A12 评估集验证识别准确率达标。
- **R10 排在 R3/R4 之后**：MCP 工具集的实现基础是导入导出能力，且需要 R13 的配额与 R14 的审计才能安全对外开放。先做最小 MCP Server 验证「被集成」的真实需求，再决定是否投入 IDE 插件（独立工程，成本高）。

**批次二的完成标准**
- 用户能看到自己的 AI 用量与剩余额度，额度耗尽时优雅降级而非报错。
- 新用户可从模板 + 主题起步，模板命中不调 LLM。
- 至少支持思维导图与时序图两种新图型，且可导出/导入 Mermaid。
- 可以上传文档或粘贴链接生成流程图。
- 外部 MCP 客户端可调用语图的核心能力。

### 5.4 批次三 · P2：团队化与专业化，按需求信号触发

| 顺序 | 建议 | 交付内容 | 触发条件 |
| --- | --- | --- | --- |
| 1 | **R14 企业合规（低成本三项先行）** | 数据留存承诺明示化 + 一键删除全部数据 + 审计日志 | 建议在 **P1 后期即先行**（成本极低，立刻可用于企业对话） |
| 2 | **R12 协作（一级 + 二级）** | 分享链接只读浏览 → 评论与 @AI 进线程 | 产品已积累足够个人用户价值；**三级实时共同编辑明确排除** |
| 3 | **R5 图片转图（第二阶段）** | 截图/照片/草图 → 可编辑图 + 低置信人在回路确认 | A12 评估集的识别准确率闸门达标；R13 额度已稳定运行 |
| 4 | **R14 企业合规（其余项）** | 权限角色 + SSO/SAML + 私有化部署包 | 首个企业客户实际需求触发；认证按客户要求按需推进 |
| 5 | **R11 数据驱动图（确定性子集）** | SQL DDL → ER 图、CSV/JSON → 批量节点 | R6 图型就绪；无外部依赖，可先验证需求 |
| 6 | **R11 数据驱动图（Git 接入）** | 代码库 → 架构图/时序图 + 增量同步 | 确定性子集需求验证通过；R10 集成范式与 R14 凭证安全就绪 |

**批次三的顺序理由**
- **R14 拆成两段**：留存承诺、一键删除、审计日志三项成本极低且是企业对话的入场券，建议在 P1 后期就先行；SSO、权限角色、合规认证则**按客户实际需求触发**，不预先投入（认证周期长、成本高且需持续维护）。
- **私有化部署包值得尽早包装**：语图「PG 单依赖 + Redis 可选 + Embedding 可降级 + trace 内置 + 布局自研」的架构，在竞品普遍绑定云厂商 AI 平台（Lucid→Azure OpenAI）或重型 SaaS（Miro）的背景下，是**尚未被产品化表达的结构性差异优势**，尤其契合国内数据本地化要求。
- **R12 严格限定为一级 + 二级**：一级（分享只读）成本极低、还带来传播曝光，可作快速项；二级（评论 + AI 进线程）是差异化机会点。**三级与「不引入重基础设施」的关键决策直接冲突，且与 A5 四级匹配存在根本性张力**（多人并发编辑使 AI 修改的匹配基线在应用瞬间即过期），明确排除。
- **R5 图片转图延后到批次三**：这是 14 条中唯一「做不好会伤害口碑」的功能，必须以评估闸门为放量前提。
- **R11 排最后**：依赖链最长（R6 图型 + R10 集成 + R13 额度 + R14 合规四项前置），且外部集成带来长期运维与代码资产安全责任，投入产出比在当前阶段偏低。先做无外部依赖的确定性子集验证需求。

### 5.5 横切要求（贯穿所有批次）

1. **评估先行**：每批次的新能力都必须同步扩充 A12 的回归评估集与 Bad Case 库，并纳入发版闸门。R9 需新增「视觉质量」评估维度，R4 需新增「导入解析准确率」，R5 需新增「多模态识别准确率」并作为放量闸门。**没有评估集支撑的功能不放量。**
2. **不引入基础设施硬依赖**：任何新增存储走 PG，可观测性走内置 trace，检索走 `tsvector` + GIN，实时通知走 SSE。允许引入应用层库（Mermaid 解析、PPTX 生成、可选的 CRDT），但不允许把 pgvector / Langfuse / Redis / ES / @antv/layout 变成必需依赖。
3. **优先复用而非新建**：本报告每条建议的「衔接点」已明确指向可复用的既有资产（A1–A16）。若某项功能无法在既有资产上扩展，应先重新评估其必要性。
4. **成本意识**：优先交付**零 Token 成本**的质量提升（R9 体检、R7 模板短路、R8 主题切换、R3 导出），再放量高成本能力（R5 多模态、R11 代码库）；高成本能力放量前 R13 必须就位。
5. **差异化叙事的一致性**：对外表达应聚焦语图真正的领先点 —— **FlowDraft 语义/呈现彻底解耦、四级降级匹配的增量修改、结构 + 视觉双层质量守门、评估驱动的发版闸门、轻基础设施可私有化**。这五点竞品公开材料中均未见同等深度的实现，是可主张的护城河；而「AI 生成一张图」本身已不构成差异。

### 5.6 批次与维度覆盖对照
